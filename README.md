# IlandyMC

**Your Minecraft Server. One Command Away.**

IlandyMC is a Python 3.11+ Linux CLI for installing and managing Minecraft Java servers.

## Supported platform and providers

- Supported OS family: Debian/Ubuntu and compatible derivatives using systemd (the host still needs VM validation).
- Providers: Vanilla, Paper, Purpur, Fabric.
- Runtime: Java is checked against the selected Minecraft version.
- UI: CLI plus a Textual TUI for server lifecycle and documented `server.properties` settings.

## Development setup

```bash
python3 -m venv .venv
. .venv/bin/activate
python -m pip install -e '.[dev]'
pytest -q
ilandy --help
ilandy doctor
```

## Install a server

```bash
ilandy doctor
ilandy install survival --software paper --version 26.3 --memory 4096 --accept-eula
ilandy start survival
ilandy status survival
ilandy logs survival
ilandy stop survival
```

The installer refuses to overwrite an existing server, stages downloads in a private directory,
checks HTTPS and available artifact checksums, then commits by same-filesystem rename. The EULA
flag is an explicit administrator confirmation. The game port defaults to 25565. Java must already
be installed and available to the invoking account.

## Backups

```bash
ilandy stop survival
ilandy backup survival
ilandy restore survival /path/to/backup.tar.gz
```

Backups are only created for stopped servers. Archives have SHA-256 sidecars; restore uses a
staging directory, rejects links and special files, validates archive paths and server identity,
and never overwrites an existing server.

## Security model

- Run under a dedicated, unprivileged account. Do not run the application as root.
- Server names and artifact filenames are validated; subprocesses use argument arrays, not a shell.
- Download URLs must be HTTPS; redirects may not downgrade to HTTP; downloads are size-limited.
- RCON is configured on loopback only with a generated per-server secret stored mode `0600`.
- PID records are checked against `/proc/<pid>/cmdline` and `/proc/<pid>/cwd` before signals.
- Settings and backup files use restrictive permissions where supported.
- The application does not open firewall ports automatically. Systemd units can be installed and managed explicitly with the `service-*` commands; this requires root on a running systemd host.

## Production readiness

IlandyMC 1.0.0 is the first stable feature baseline. It is **not yet production-certified**: live Minecraft/RCON and clean-VM acceptance gates remain open. Minecraft Java Edition 26.x is supported by the version parser and requires Java 25; Paper downloads use the stable-only Fill v3 API.
The offline test suite is exercised in CI; see `DEVELOPMENT_STATUS.md` for the latest verified count. Local tests do not
replace integration tests on clean Debian/Ubuntu VMs. Remaining release gates include: full RCON
protocol integration against actual Paper/Vanilla processes; dedicated service-account provisioning
and systemd unit installation; safe multi-instance port allocation and firewall UX; Forge/NeoForge;
transactional Minecraft server updates and rollback; scheduled backup retention; plugin/mod installation and
dependency resolution; full TUI workflows; distro/version matrix testing; dependency and security
audits; signed release artifacts and reproducible packaging.

Do not expose RCON or server management ports to the public internet. Provider APIs and Minecraft
compatibility policies can change; validate the chosen build before deployment.

## Version-aware server.properties detection

A new server is first launched once in its private staging directory. That exact Vanilla/Paper/Purpur/Fabric build generates its own `server.properties` and initial world; IlandyMC then stops it cleanly and compares the generated keys with the documented settings catalogue. Only keys that the installed build actually generated are exposed in `ily` and accepted by the CLI. Missing keys are hidden, never injected, so a setting unknown to an older Minecraft release cannot break or confuse it. Unknown/native keys generated by the server remain in the file when saving.

The bootstrap launch binds to loopback and uses port `0`, with RCON disabled, so it does not expose a public game listener. After bootstrap, IlandyMC applies managed values only where the target server generated those keys, including `online-mode=false` by default and loopback RCON when supported. If the server cannot reach its ready state or stop cleanly, installation is aborted before the staging directory is committed. The uploaded 26.3 catalogue supplies labels and descriptions, not the list of active settings. Because `online-mode=false` disables Mojang/Microsoft account authentication at the server, expose the server only behind an authenticated proxy (for example, a correctly configured Velocity setup) or use another trusted authentication layer; never allow players to connect directly to the backend.

Open the editor and use **Save all settings**. The list is scrollable. The RAM limit remains a launch setting; gameplay port and all other Minecraft properties are edited in the same property list.

CLI inspection and edits are also available (repeat `--set` for multiple keys):

```bash
ilandy server-properties survival
ilandy server-properties survival --set online-mode=false --set max-players=30 --set difficulty=hard
```

Choose the Minecraft TCP port during installation (1024–65535):

```bash
ilandy install survival --software paper --version 26.3 --memory 4096 --port 25565 --accept-eula
```

On a systemd Linux host, install the service as root. This creates or reuses a dedicated
unprivileged `minecraft` system account, transfers ownership of the managed server directory,
installs a hardened unit, and enables/starts it:

```bash
sudo ilandy service-install survival
ilandy service-status survival
sudo ilandy service-uninstall survival
```

Use `sudo ilandy service-install survival --no-enable` to install without starting it. The
service commands require root and a running systemd host. They do not open firewall rules,
remove the service account, or delete server data. Existing units are never overwritten.

The systemd workflow is implemented and covered by offline tests, but still requires acceptance
on clean Debian/Ubuntu VMs before production certification. Port availability can change between
installation and server startup; firewall configuration remains an explicit administrator task.


## Launch the TUI and install the application

Install the reviewed source tree under `/opt/ily` (requires root):

```bash
sudo bash bootstrap/install.sh .
ily
```

`ily` opens the Textual management UI. Select a server to start/stop it, edit RAM and all documented
`server.properties` options while stopped, inspect its status, and check for application updates. The `ilandy` CLI
remains available for scripts and automation. Server data remains under `/opt/ilandy/servers`;
`/opt/ily` contains only the application virtual environment.

### Automatic application updates

Updates are opt-in and default to disabled. Publish a JSON manifest over HTTPS, for example:

```json
{
  "version": "0.8.1",
  "url": "https://example.invalid/releases/ilandymc-0.8.1-py3-none-any.whl",
  "sha256": "<64-character-sha256-of-wheel>"
}
```

Configure the manifest URL and opt in:

```bash
ilandy config --manifest-url https://your-domain.example/ilandymc/manifest.json --auto-update
```

The `ily` launcher checks the manifest on startup and applies a newer wheel only after checking
its SHA-256. Redirects are disabled; both manifest and wheel must be served over HTTPS. The
updater only manages installations made into `/opt/ily/venv`. If the manifest is unavailable or
invalid, the UI still starts and reports the update failure. Disable with `ilandy config --no-auto-update`.

### Server settings

```bash
ilandy server-config survival                 # show settings
ilandy server-config survival --memory 4096 --port 25575
ilandy start survival
ilandy stop survival
ilandy status survival
```

Settings can only be changed while stopped. If a systemd unit is installed, its memory setting
is regenerated and systemd is reloaded. The TUI provides the same start/stop, RAM, and `server.properties` controls.
